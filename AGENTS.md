# dotfiles

Linux (CachyOS/Arch) dotfiles managed with GNU Stow. Not a software project — no build/test/lint/CI.

## Stow layout

Each top-level directory is a Stow package. Run from repo root:

```
stow <package>
```

This symlinks `./<package>/.config/<app>/...` → `~/.config/<app>/...`. Example: `stow nvim` links `nvim/.config/nvim/` → `~/.config/nvim/`.

Packages: `awesome`, `bash`, `clipcat`, `fish`, `fonts`, `gtk`, `kitty`, `nvim`, `pandoc`, `picom`, `systemd`, `tv`, `udiskie`, `opencode`, `xdg`, `xprofile`.

## Key facts

- **Shell**: fish with `pure` prompt, `fisher` plugin manager, `eza` for ls. Bash `.bashrc` is minimal (interactive-only).
- **WM**: AwesomeWM with Catppuccin Mocha theme, `Mod4` as primary key. No in-`rc.lua` autostart; two-phase systemd startup: infra (picom, clipcatd, xremap) as user units `WantedBy=graphical-session.target`, pulled in via the `graphical-login.target` wrapper from `~/.xprofile`; GUI apps (throne, telegram, discord, steam, superproductivity, firefox, obsidian, menu) as units `WantedBy=graphical-apps.target`, started by a hook at the end of `rc.lua` so they never race WM init (cursor theme, EWMH, tray). All app units use `Restart=always` + `StartLimitIntervalSec=0` — a closed window comes back; stop for real with `systemctl --user stop <name>`. `RestartSec` is split by class: `100ms` for GUI app units (`graphical-apps.target`, so a closed window is back essentially instantly), `500ms` for throne (it re-creates a TUN device, so 100ms races the teardown) and `1s` for infra units (`graphical-session.target`: picom, clipcat, xremap) — `StartLimitIntervalSec=0` means a unit that dies at startup would otherwise crash-loop at the GUI rate and burn a core on compositor/input/clipboard respawns. throne must run fully elevated (`ExecStart=sudo -n ...`) — unprivileged it tries to raise the core itself (`chown root:root` + `chmod u+s` on `ThroneCore`) and then the core goes silent: no `Core Has Successfully Connected` handshake, no `throne-tun`, so don't drop sudo. The tree is therefore uid 0 and `systemctl --user` cannot signal it (`EPERM`, `Failed to kill control group`), so it cannot clean up after itself either; the unit reaps its own leftovers with `sudo -n pkill -9 -x -f <exact path>` in `ExecStartPre`/`ExecStopPost`, allowed by `/etc/sudoers.d/throne-restart` (exact args — a trailing `*` would let root kill any process). The existing `NOPASSWD` rule for the Throne binary and its `Defaults!.../Throne env_keep+="XCURSOR_THEME XCURSOR_SIZE"` must stay: `ExecStart` and the cursor theme need them. Two traps: `config/logs/throne.log` is buffered and only flushes on exit, so never judge startup by tailing it; and `throne-tun` exists only while Tun Mode is enabled in the app's UI, which is what `discord.service`'s `ExecStartPre` gates on. discord additionally waits for `throne-tun` via `ExecStartPre` + `Wants=throne.service` (start ordering only, no stop propagation). nm-applet/blueman-applet are intentionally not installed (Wi-Fi via `tv wifi` + nmcli, BT via bluetoothctl).
- **Terminal**: kitty, exported once as `TERMINAL` from `xdg/.profile` (SDDM sources it before Awesome, so GUI shells inherit it); `rc.lua` and tv channels fall back to `kitty` when unset (TTY/ssh).
- **Editor**: nvim (LazyVim) with extras: mini-surround, mini-move, json, markdown, python, toml. Stylua format: spaces, indent 2, width 120.
- **Launcher**: tv channels. Brightness, clipboard (clipcat via `tv clipboard`), power and wifi live in `tv` channels. Firefox bookmarks moved to `tv bookmarks` (foxmarks + xdg-open), launched from `tv menu`. Web search is a `web-search.sh` helper under `tv/.config/television/scripts/`, launched from `tv menu`. Everything menu-like opens in the prewarmed menu window (next bullet), not a fresh kitty.
- **Menu window**: one dedicated kitty window (`WM_CLASS=menu`, `menu.service` in `graphical-apps.target`) stays alive for the whole session and is kept hidden by awesome — `hidden` in the rule is applied on `manage`, i.e. before the first map, so the window never flashes at spawn. `menu.lua` is the WM side (show, `request::activate`, hide, autoclose on `unfocus`, ignore-while-busy, `systemctl --user start`/`restart` when the window is gone: systemd owns spawning, lua must not, or two servers would race on the FIFO); `awesome/.config/awesome/scripts/menu` is the terminal side — it blocks on the FIFO `$XDG_RUNTIME_DIR/awesome-menu/request`, runs the command on the pty and reports back with `awesome-client "require('menu').event('busy'|'done', rc)"` (arbitrary X properties emit no signal in awesome, so this is the only reverse channel). A request is two lines, mode + command; `menu --send "<cmd>"` queues a follow-up, which is how the `menu` channel chains menu → brightness → … into one window instead of spawning a kitty per step. After a command exits the wrapper peeks the FIFO for 50ms: a queued follow-up is found instantly and the window stays up, an empty FIFO only costs the 50ms right before the window hides anyway. tv is not special-cased (tv renders on stderr and prints the selection on stdout), and menu-like channels only chain *terminal* follow-ups (a tv channel, `nvim`, `read`) — GTK apps still get their own `setsid kitty` window, and so do `apps`/`bookmarks`, which are launchers rather than flows. Traps: `read -t ''` is not "no timeout" in bash 5.3 (use plain `read -r -u 3`; the FIFO is held `exec 3<>` so writers never block and there is no EOF), `awful.rules` documents an `ontop` property that does not exist in 4.3 (use `above`), and `menu --send` falls back to a throwaway `kitty --class tv` window when no server holds the lock, so the channels keep working without the unit. The window **autocloses on focus loss** (`client.connect_signal("unfocus", ...)` — awesome 4.3 emits `focus`/`unfocus`, there is no `property::focus`; the same signal comes out of `banning_need_update` when our own `hide()` runs, which is why `hide(c)` takes the client and no-ops when it is already hidden): clicking another window, a focus hotkey or a window that steals the focus (firefox from `tv bookmarks`) hides it even mid-flow, and the command keeps running headless. That would strand the menu, since `busy` stays set until the wrapper reports `done`, so the next `menu.open` with the window hidden **restarts the unit** instead of queueing behind the abandoned flow — systemd stops the control group, which reaps that command (and anything it launched that is still in it: a `setsid kitty` window is detached from the tty but not from the cgroup), and `pending` survives `unmanage` so the fresh window picks the request up. Killing the abandoned flow is deliberate; the alternative (restore the window) makes the menu key hand back whatever was still running. Showing it needs `lower()` before `request::activate{raise=true}`: `luaA_client_raise()` (awesome 4.3, `objects/client.c`) returns early when the client already sits at the end of `globalconf.stack`, and nothing ever takes the prewarmed window off that list, so from the second open on no restack was even scheduled and the remapped window landed under whatever was focused last. The order inside `awesome_refresh()` is what makes that restack survive unhide: `stack_windows()` only sets a flag, the actual ConfigureWindow requests go out in `stack_refresh()`, i.e. after `banning_refresh()` mapped the window. Focus needs its own nudge for the same reason — `SetInputFocus` against a not-yet-mapped window is a BadMatch, so `menu.open` re-activates once from a 50ms timer, guarded by `not c.hidden and client.focus == c` (awesome's own re-issue in `client_unban()` only happens while the menu is still the focus target). Switching workspace closes the menu too, via `tag.connect_signal("property::selected")` — the window is sticky, so it would otherwise follow the user to the other tag. The prewarmed window also replaces the old `kitty --class tv` menu windows, which input remapping matched by class: `xremap --list-windows` reports it as `menu.menu`, so every `tv.tv` in `xremap/.config/xremap/config.yml` became `menu.menu` (the TV word/line ops `only`, and the `not` exclusion of the Ctrl+C/V/X/Z disabling rule). The `/kitty/` rules were deliberately left alone: the window is a kitty window that no longer calls itself `kitty.*`, so it takes exactly the path the tv windows took — Super-C/V/A become Ctrl-C/V/A (no kitty copy/paste) and Ctrl+C/V/X/Z are not suppressed. Note that XTEST events (`xdotool key/type`) never reach xremap, which grabs evdev devices, so remap behaviour cannot be verified that way — use a uinput device (xremap auto-selects by capability, so a uinput keyboard with a minimal key set is listed but not grabbed; copy the capabilities of an already-selected virtual keyboard), and remember `Ctrl-BackSpace` is claimed by both the TV rule (`Alt-u` → tv `delete_line`) and the "delete to line start" rule: the first matching keymap wins, so in tv/menu it deletes the whole input line and the latter rule is dead code there.
- **TV**: television terminal viewer with extensive channel configs under `tv/.config/television/cable/`.
- **Notifications**: there is no dunst/notify-send daemon to look for — **awesome is the notification daemon**. It owns `org.freedesktop.Notifications` on the session bus (`busctl --user list | grep Notifications` → PID of awesome) and renders notifications as naughty popups; its `GetCapabilities` include `actions`, so libnotify action buttons work, which is why udiskie's "Browse directory"/"Mount" buttons and `notify-send -A` are usable. dunst is installed, is not running and is *not* what answers on the bus. This also means `awesome-client` is only needed for state that libnotify cannot express (the menu window's busy/done events in `menu.lua`).
- **Removable media**: `udiskie` (in the CachyOS `extra` repo, not AUR; needs `python-docopt`) automounts flash drives/cards/discs through udisks2. Volumes are mounted under `/run/media/$USER/<label>`, and `~/Media` is a machine-local symlink to that directory (created by hand, like the `*.target.wants/` symlinks) for a stable short path. udisksd hardcodes `/run/media` — the only trace of it in the binary is the error string `Error creating directory /run/media: %m`; there is no env var and no config file, so a symlink is the only way to get a path of one's choosing without patching. udiskie resolves it fine: `Device.is_file()` compares paths with `os.path.samefile()`, so `udiskie-mount`/`udiskie-umount` accept `~/Media/<label>`. Two caveats: `/run` is a tmpfs, so after a reboot `~/Media` dangles until something is plugged in for the first time (udisks2 creates `/run/media/$USER` lazily, and `/run/media` is root-owned 0755 so it cannot be pre-created from a user unit — a root `/etc/tmpfiles.d` rule is the only way to make it permanent, and udisks2 would then skip its own creation and its ACL), and the `tv media` channel deliberately lists the canonical `/run/media/$USER` rather than `~/Media`, so that deleting the symlink cannot silently break it. Driven by the `udiskie` stow package (`~/.config/udiskie/config.yml`, `scripts/browse`, `scripts/eject`) plus `udisksie.service` in `graphical-session.target` (infra class: `Restart=always`, `RestartSec=1s`, `StartLimitIntervalSec=0`). `automount` and `notify` are on, `tray` is off (awesome has no tray applets), and the only `device_config` rule is a catch-all `options: [noatime]` — udisks2 mounts removable media `relatime`, which still writes an inode access time on every read. `file_manager` (the target of the mount notification's "Browse directory" button) is passed in the unit, not in `config.yml`, because it needs `%h` and only systemd expands specifiers in `ExecStart`; it points at `scripts/browse`, which puts the volume into the prewarmed menu window with yazi (`require('menu').open(..., 'hold')`, `hold` because yazi owns the window until it exits) instead of the `xdg-open` default, which would resolve `inode/directory` through `mimeapps.list`. Traps: (1) with `--eject --detach` the exit code of `udiskie-umount` is the *detach* one, because a flash drive is detachable but not ejectable, and a busy mount point fails in ways the code alone does not distinguish — `scripts/eject` therefore asks the mount point itself (`mountpoint -q`) and reports through `notify-send`, critical on failure; (2) a failed safe-remove produces no udiskie event — the events are mounted/unmounted/locked/unlocked/added/removed — so `scripts/eject` sends its own `notify-send`, critical on failure; it has to, because the menu window hides itself the moment the command it runs exits, so stdout is never read (udiskie's `job_failed` popup does cover failures of the automount itself); (3) the physical unplug is not udiskie's to handle: udisks2 drops the mount when the device disappears, and powering the drive off is only meaningful *before* unplugging, which is why "poweroff" lives in `tv media` → `ctrl-e` and not in a removal hook; (4) nothing internal gets mounted, and that is udiskie's builtin rules, not ours: they drop non-external toplevel devices, the root filesystem, loop devices and the docker mapper symlinks, and a catch-all rule that only sets `options` cannot unignore them (verified against `udiskie.config.match_config`); (5) a stow symlinked unit that has not been enabled reports state `linked` with an empty `FragmentPath` — that is normal (`nextcloud-sync@.service` looks the same), not a broken symlink.
- **Pandoc**: Eisvogel template files under `pandoc/.local/share/pandoc/templates/` — symlinked to `~/.local/share/pandoc/templates/` (not `.config`).
- **Secrets**: `~/.config/.env` is sourced by bash and fish but **not tracked** in repo. Also `~/.fish_profile` is expected but not tracked.
- **XDG**: base-directory defaults live in the `xdg` stow package (`xdg/.profile`, `.config/mimeapps.list`, `.config/user-dirs.dirs`, `.config/environment.d/10-xdg.conf` for user services). Fish never sources `.profile`, so it gets `set -q` guards via `fish/.config/fish/conf.d/xdg.fish`.
- **Fonts**: fontconfig config enables JetBrains Mono (likely).
- **OpenCode** config at `opencode/.config/opencode/opencode.json` — permission rules for git/ls/pwd.

## Development

Nothing to build, test, lint, or format. Changes are applied by re-running `stow <package>` or by symlinking manually. To preview file changes before commit, use `git diff`.

Systemd units live in the `systemd` package, but enablement state (`*.target.wants/`) is machine-local and gitignored. After `stow systemd`, enable explicitly: `systemctl --user daemon-reload && systemctl --user enable --now clipcat.service`. NEVER run `systemctl --user disable/reenable` on stow-managed units: disable cannot tell the stow symlink apart from an enablement symlink and deletes `~/.config/systemd/user/<unit>` itself (recover with `stow systemd` + `daemon-reload` + `enable`); to move a unit between targets, `enable` the new target and `rm` the old `*.target.wants/` symlink manually. Graphical-session-bound services (`clipcat`, `xremap`) are pulled in via the `graphical-login.target` wrapper started from `~/.xprofile` (stow package `xprofile`, sourced by SDDM Xsession before the WM): stock `graphical-session.target` has `RefuseManualStart=yes`, so it can only be activated as a dependency (`Requires=` in the wrapper), never via `systemctl start` directly. Logout is the `logout` fish alias (stops the target, then `awesome-client 'awesome.quit()'` for a graceful WM shutdown), invoked directly and from the `tv power` Logout action via `fish -c` — no per-service `start`/`restart` calls anywhere, no helper scripts, and no bare `awesome.quit` keybinding. (`loginctl terminate-session` was tried but reverted: the harsh SIGKILL made Discord dump a ~10 GB core, freezing the machine under systemd-coredump; `systemctl --user exit` was also rejected — it only quits the user manager, leaving Awesome/X running.) `clipcat.service` cleans its pid file in `ExecStopPost` to avoid stale-pid wait loops after unclean stops. Note: stow folds a package dir into one symlink when the target path is new — if `~/.config/systemd/user` ever becomes a single symlink into the repo, `systemctl enable` will write absolute symlinks into the repo; fix by `stow -D systemd`, `mkdir -p ~/.config/systemd/user`, `stow systemd` (per-file symlinks), then enable again.
